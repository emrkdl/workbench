01시스템 정의와 용어

"대시보드"가 아니라, PCB 설계 데이터에 특화된 자산 관리 시스템 + 뷰어 + 비교 도구다.

BoardLens는 세 가지 일을 한다. 이 셋이 한 시스템 안에 있어야 하는 이유는, 셋 다 같은 파싱 결과를 소비하기 때문이다. 파일을 따로 열어보는 뷰어와 스펙을 따로 적어두는 위키를 각각 운영하면 둘은 반드시 어긋난다.

Manage

설계 파일을 리비전 계보와 함께 적재하고, 상태·권한·이력을 관리한다.

Inspect

보드 스펙과 실제 레이아웃을 CAD 툴 없이 브라우저에서 열람한다.

Compare

두 리비전의 부품·회로·기하 변경을 자동으로 산출한다.

용어 정의

이후 모든 문서와 코드에서 아래 용어를 고정해서 쓴다. 특히 Board와 Revision의 분리가 데이터 모델 전체를 좌우한다.

용어식별자정의
Projectproject제품 또는 개발 과제 단위. 권한 부여의 기본 경계.
Boardboard하나의 설계 계보. 리비전이 바뀌어도 유지되는 논리적 정체성 (예: MAIN-A1).
Revisionrevision특정 시점의 설계 스냅샷. 실제 데이터는 전부 여기 매달린다. 열람·비교의 단위.
Design Filedesign_file업로드된 원본 HKP. 불변, sha256으로 주소 지정.
CDMcdmCanonical Design Model. CAD 포맷과 무관한 사내 중립 스키마.
ChangeSetchangeset두 리비전 비교 결과. 캐시 가능한 산출물.
범위 밖

편집·설계 기능은 넣지 않는다. BoardLens는 읽기 전용이다. DRC 재실행, 시뮬레이션, 거버 생성은 기존 CAD 툴의 몫이며, 그 결과물을 첨부·표시만 한다. 이 경계를 흐리면 CAD 툴의 열등한 복제품이 된다.

02아키텍처

인제스트 · 저장 · 서빙 3계층. 기하 데이터는 API를 우회해 브라우저로 직행한다.

구성 요소

컴포넌트역할배치
bl-coreREST API. 카탈로그 검색, 리비전 상세, ChangeSet 조회, 권한 판정, 감사 기록.컨테이너 1~2

설계 결정

Redis·Celery 대신 PostgreSQL 잡 테이블 + SELECT … FOR UPDATE SKIP LOCKED를 쓴다. 폐쇄망 온프렘에서는 운영 인력이 붙는 미들웨어 하나하나가 비용이다. 하루 수십 건 규모의 인제스트에 별도 브로커는 과잉이고, 잡 상태를 같은 트랜잭션에서 보는 편이 재파싱·실패 추적도 단순하다. 처리량이 문제가 되는 시점에 교체하면 되고, 그 시점은 오지 않을 가능성이 높다.

03캐노니컬 디자인 모델 (CDM v1)

이 문서에서 가장 중요한 섹션. HKP 실물이 없는 지금이 오히려 포맷 비의존 모델을 강제할 최적의 시점이다.

DB 스키마도 API도 UI도 HKP를 직접 알지 못한다. 아는 것은 CDM 하나뿐이고, HKP는 그 CDM을 만들어내는 여러 입력 중 첫 번째일 뿐이다. 이렇게 두면 나중에 ODB++나 IPC-2581, 혹은 다른 CAD의 ASCII 출력이 들어와도 어댑터만 추가하면 된다. 반대로 HKP 필드명이 그대로 컬럼명이 되어버리면 두 번째 포맷이 들어오는 날 전체를 다시 짜야 한다.

단위와 좌표계 규약

이 규약을 코드로 고정하지 않으면 비교 기능에서 반드시 사고가 난다. 부동소수점 좌표를 두 리비전에서 뺄셈하면 0.09999999 같은 값이 나오고, 그러면 아무것도 안 바뀐 부품이 "이동함"으로 잡힌다.

항목규약이유
길이 단위정수 나노미터 (nm)부동소수 누적 오차 제거. 비교가 정확히 ==로 성립한다. int64로 ±9,200 km까지 표현 — 어떤 보드도 넘지 않는다.
표시 단위mm (기본) / mil (토글)변환은 표시 직전에만. 저장·연산 경로에는 절대 들어오지 않는다.
원점보드 외형 좌하단CAD마다 원점이 제각각이므로 인제스트 시점에 정규화. 리비전 간 좌표 비교의 전제.
축 방향X 우측, Y 상방향수학 좌표계. 화면 렌더 시에만 Y를 뒤집는다.
각도1/1000 도, 반시계0~359,999. 회전 변경 판정도 정수 비교.
레이어 번호1부터, Top이 1물리 적층 순서. CAD 레이어명은 source_name에 원본 보존.

핵심 엔티티 필드

전체 스키마는 cdm/schema/cdm.v1.json이 단일 정의(single source of truth)이고, Pydantic 모델과 TypeScript 타입을 둘 다 거기서 생성한다. 손으로 두 번 쓰면 반드시 어긋난다.

DesignHeader

필드타입설명

Net · NetPin

필드타입설명

HKP 실물 확보 전 대응

파서는 parse(text) -> CDM 하나만 노출하는 인터페이스로 못박고, 실물이 오기 전까지는 골든 픽스처 테스트만 준비한다. 즉 "이 입력 텍스트가 들어오면 이 CDM이 나온다"는 케이스 파일을 만들어 두고, 실제 HKP를 받으면 픽스처를 실물로 교체한다. CDM 쪽 코드는 한 줄도 바뀌지 않는다.

04저장 설계와 규모 산정

1,000 리비전 규모에서 무엇이 몇 행이 되는지 먼저 계산하고, 그 숫자에 맞춰 저장 방식을 나눈다.

규모 추정

보드 1장당 부품 2,000개 · 넷 3,000개 · 핀 20,000개 · 기하 객체 200,000개를 중간값으로 잡았다 (8층 고밀도 보드 기준). 리비전 1,000장 기준:

데이터보드당총계 (1,000)저장 위치판정
Revision11,000PostgreSQL여유
Component2,0002,000,000PostgreSQL여유
Net3,0003,000,000PostgreSQL여유
NetPin20,00020,000,000PostgreSQL인덱스 설계 필요
기하 객체200,000200,000,000Blob (.blg)DB 부적합
원본 HKP~30 MB~30 GBBlob여유
.blg 버퍼~8 MB~8 GBBlob여유

결론: PostgreSQL 약 15 GB, Blob 약 40 GB. 단일 서버 한 대로 충분하다. 분산 저장이나 검색 엔진 도입을 정당화할 규모가 아니며, 폐쇄망 운영 부담만 늘린다.

파티셔닝

net_pin과 component는 revision_id 기준 해시 파티션. 어떤 질의든 리비전이 먼저 좁혀지므로 파티션 프루닝이 그대로 먹는다.

summary jsonb

카탈로그 목록은 보드당 20여 개 집계값을 보여준다. 매번 집계하면 느리므로 인제스트 시점에 계산해 리비전 행에 박아둔다.

불변성

리비전은 한 번 ready가 되면 수정하지 않는다. 재파싱은 새 parser_version으로 내용을 갈아끼우되 리비전 ID와 링크는 유지한다.

.blg — 레이어 기하 버퍼

레이어 하나당 파일 하나. 브라우저가 받아서 파싱 없이 그대로 Int32Array 뷰를 씌워 GPU로 올릴 수 있는 형태로 만든다.

// .blg v1 레이아웃
[ magic "BLG1" | u32 ]  [ layer_index | u16 ]  [ object_count | u32 ]
[ bbox: x0,y0,x1,y1 | i32 x4 ]
[ kind_offsets: trace, pad, via, plane, text | u32 x5 ]
[ coords: i32[] ]      // nm 단위 정수 좌표, 종류별로 연속 배치
[ attrs:  u32[] ]      // net_id · width · flags 팩
// 전체를 gzip. nginx가 Content-Encoding: gzip으로 그대로 서빙 → 서버 CPU 0

05인제스트 파이프라인

파서는 앞으로 계속 고쳐진다. 전체 재파싱이 일상 작업이라는 전제로 설계한다.

검증 규칙

CDM 스키마 검증을 통과해도 의미상 깨진 데이터는 들어올 수 있다. 인제스트 마지막에 무결성 규칙을 돌리고, 위반은 실패가 아니라 경고로 기록해 리비전 상세에 띄운다 — 실제 설계 데이터는 원래 조금씩 지저분하고, 그걸 이유로 적재를 거부하면 시스템을 아무도 안 쓴다.

규칙처리
부품 좌표가 보드 외형 밖경고 배치 오류이거나 원점 정규화 실패 신호
핀이 0개인 넷경고 고아 넷으로 표시, 넷 수 집계에서 별도 계상
RefDes 중복실패 Diff 매칭 키가 깨지므로 적재 불가
스택업 인덱스 불연속실패 층 구조 해석 불가
외형 폴리곤 미폐합경고 자동 폐합 시도 후 기록

07뷰어

20만 객체를 60fps로 팬·줌하는 것이 목표. 이 목표가 앞선 저장 설계를 강제했다.

기능동작
레이어 제어on/off, 색상, 투명도, 단독 보기(solo), 순서 반전. 프리셋 저장.
넷 하이라이트넷 클릭 → 전 레이어 관통 하이라이트 + 나머지 디밍. 넷 정보 패널 동시 표시.
부품 검색RefDes 입력 → 즉시 zoom-to-fit + 속성 팝업.
측정두 점 거리, 두 객체 간 최소 간격(클리어런스).
보기 옵션Top/Bottom 전환(미러), 90° 회전, 그리드, 커서 좌표(mm/mil 토글), 미니맵.
마크업좌표에 코멘트 핀. 리뷰 스레드로 연결.
딥링크뷰 상태(레이어·줌·선택·하이라이트)를 URL에 담아 그대로 공유.
성능 목표

8층 20만 객체 보드 기준 — 첫 화면 표시 2초 이내, 팬·줌 60fps, 레이어 토글 16ms 이내. 미달 시 서버 사이드 타일 렌더링을 대안으로 두되, 폐쇄망에서 서버 GPU를 기대하기 어려우므로 클라이언트 WebGL이 1순위다.

08Diff 엔진

이 시스템이 파일 서버와 갈라지는 지점. 핵심은 "무엇을 같은 것으로 볼 것인가"다.

비교의 어려움은 픽셀 비교가 아니라 매칭에 있다. 넷 이름이 VDD_1V8에서 VDD_CORE로 바뀌었을 때, 이름만 보면 "넷 하나 삭제 + 넷 하나 추가"로 잡힌다. 그러면 설계자에게는 쓸모없는 노이즈가 된다. 실제로 알고 싶은 것은 회로가 바뀌었는가이지 문자열이 바뀌었는가가 아니다.

매칭 규칙

대상1차 키2차 키판정 결과
Componentrefdespart_number + 좌표 근접added / removed / moved / rotated / flipped / replaced
Netnamesignature (핀셋 해시)added / removed / renamed / rewired
NetPin(net, refdes, pin)—집합 차집합 = 진짜 회로 변경
StackupLayerindexrole + 두께inserted / removed / spec_changed
Geometry레이어 · 공간 셀 해시—변경 영역 bbox 목록

부품 이동 판정에는 임계값을 둔다. 기본 10 µm 미만은 변경으로 보지 않는다 — CAD 재저장만으로도 하위 자릿수는 흔들리기 때문이다. 임계값은 UI에서 조정 가능하게 노출한다.

기하 비교

레이어를 격자로 나눠 셀마다 그 안의 객체를 해시한다. 두 리비전에서 해시가 다른 셀만 모아 변경 영역 목록을 만든다. 이렇게 하면 "이 리비전에서 실제로 손댄 곳이 어디인가"를 즉시 짚어줄 수 있고, 뷰어는 그 bbox로 자동 이동한다. 전체 픽셀 비교보다 훨씬 싸고, 결과가 좌표라서 UI가 바로 쓸 수 있다.

비교 화면

Side-by-side

두 뷰포트를 잠금 동기화. 팬·줌·레이어 선택이 함께 움직인다.

Overlay

A만 = 구리색, B만 = 청록색, 공통 = 회색. 배선 변경을 한눈에 본다.

Swipe

수직 분할선을 드래그. 미세한 위치 변화 확인에 가장 정확하다.

Blink

일정 주기로 A/B 교차 표시. 잔상으로 차이가 튀어나온다.

ChangeSet은 (rev_a, rev_b, parser_version) 키로 캐시한다. 자주 보는 조합은 두 번째부터 즉시 뜨고, 파서가 갱신되면 자동 무효화된다. 변경 요약은 PDF·CSV로 내보내 설계 변경 문서에 그대로 붙일 수 있게 한다.

09검색과 인사이트

보드가 쌓일수록 가치가 커지는 기능들. 여기서 시스템이 "저장소"에서 "자산"으로 바뀐다.

부품 역검색 — 우선순위 최상

"이 파트넘버를 쓰는 보드를 전부 찾아라." 단종(EOL) 공지가 뜰 때마다 설계팀이 수작업으로 하던 일이고, BoardLens에서는 part 마스터 테이블 조인 한 번이다. 결과는 보드 목록 + 각 보드에서의 사용 수량 + 해당 부품 위치로의 딥링크.

정확도의 관건은 파트넘버 정규화다. 같은 부품이 GRM188R71H104KA93D와 GRM188R71H104KA93로 들어오면 다른 부품이 된다. 인제스트 시 제조사 + MPN 정규화 규칙(공백·하이픈·포장 접미사 제거)을 적용하고, 정규화 규칙은 데이터로 관리해 나중에 고칠 수 있게 한다.

유사 보드 찾기

신규 설계 착수 시 "비슷한 걸 전에 만든 적 있나"에 답한다. 층수·면적·부품 밀도·최소 선폭·BGA 최소 피치·비아 종류를 정규화한 가중 거리로 순위를 매긴다. 초기에는 학습 없는 단순 가중 스코어로 충분하고, 가중치는 설정으로 노출한다.

포트폴리오 통계

  • 연도별 신규 리비전 수, 층수 분포, 면적 분포
  • 설계 룰 세대 추이 — 최소 선폭·최소 드릴·BGA 피치가 시간에 따라 어떻게 미세화됐는지
  • 부품 재사용률 — 여러 보드에 걸쳐 쓰이는 부품의 비율. 표준화 수준을 나타내는 지표
  • 복잡도 스코어 — 밀도·층수·핀 수를 합성한 단일 지표로 보드 간 난이도 비교

이 통계 화면들이 흔히 말하는 "대시보드"에 해당하지만, 전체의 한 페이지일 뿐이다. 시스템의 무게 중심은 카탈로그·뷰어·비교에 있다.

10권한과 감사

PCB 설계 데이터는 회사의 핵심 자산이다. 폐쇄망이라는 사실이 접근 통제를 면제해주지 않는다.

역할권한
Viewer허용된 프로젝트의 메타·뷰어·비교 열람. 원본 파일 다운로드 불가.
EngineerViewer + 원본 다운로드, 코멘트·마크업 작성.
MaintainerEngineer + 업로드, 리비전 상태 변경, 재파싱 트리거.
Admin전체 + 권한 관리, 감사 로그 열람.

권한 경계는 프로젝트다. 보드 단위 예외는 두지 않는다 — 관리 비용 대비 실효가 없고, 예외가 쌓이면 아무도 현재 상태를 모르게 된다.

인증

초기에는 로컬 계정. 사내 AD/LDAP 연동 지점을 AuthProvider 인터페이스로 미리 뚫어둔다.

감사 로그

원본 다운로드·권한 변경·업로드는 예외 없이 기록. 누가·언제·무엇을·어느 IP에서.

워터마크

뷰어 화면에 사용자 ID를 옅게 겹쳐 렌더. 화면 촬영 유출에 대한 최소한의 억제책.

12로드맵

HKP 실물 없이 진행 가능한 구간이 Phase 2까지다. 그 구간을 먼저 다 끝낸다.

단계내용HKP 필요
Phase 0CDM v1 확정 · 코드 생성 · 목데이터 생성기 · 웹 셸불필요
Phase 1카탈로그(파셋 검색) · 리비전 상세(Overview·Stackup·Components·Nets·Revisions)불필요
Phase 22D 뷰어 — 레이어 제어 · 선택 · 넷 하이라이트 · 측정불필요
Phase 3Diff 엔진 + 비교 화면 4모드 + 변경 리포트불필요
Phase 4부품 역검색 · 유사 보드 · 포트폴리오 통계불필요
Phase 5HKP 파서 실장 · 백엔드 연결 · 권한 · 감사 · 오프라인 배포필수
이 순서인 이유

목데이터를 CDM 규격에 맞춰 생성해두면 Phase 1~4의 모든 화면이 실제 데이터와 동일한 형태를 소비한다. Phase 5에서 파서가 붙는 순간 목데이터 로더를 API 호출로 바꾸는 것 외에 고칠 것이 없다. 반대로 파서를 기다리며 멈춰 있으면 아무것도 진행되지 않는다.

Phase 0 작업 목록

  1. cdm/schema/cdm.v1.json — 단위·좌표계 규약을 포함한 전체 스키마
  2. 코드 생성 스크립트 — 스키마 → Pydantic 모델 + TypeScript 타입
  3. tools/mockgen — 리비전 계보가 있는 가짜 보드 30장 생성. 부품·넷·핀·스택업·DRC·기하까지 포함하고, 일부는 의도적으로 서로 다른 리비전으로 만들어 Diff 개발에 쓴다
  4. 웹 셸 — 라우팅, 디자인 토큰, 레이아웃, 목데이터 로더
  5. 카탈로그 화면 — 파셋 필터 · 테이블/카드 전환 · 정렬 · 가상 스크롤
  6. 리비전 상세 — Overview · Stackup · Components · Nets · Revisions
  7. Viewer · Compare · Insights는 라우트와 자리만 잡아둔다
